초기 기획 단계에서 생각했던 것보다 사용자 입장에서 필요한 추가 기능이 많아지면서 프로젝트의 범위가 계속 커지는 점이 가장 어려웠습니다. 또한 기능을 계속 추가하다 보니 문서와 Schema에는 정의되어 있지만 실제 코드와 조금씩 다른 부분이 생겨 이를 하나씩 확인해야 했습니다. 이를 해결하기 위해 기능을 단순히 추가하는 방식이 아니라 문서, Schema, 소스, 테스트를 서로 비교하면서 검증했고 실제 Windows 환경에서 전체 테스트를 반복해 문제가 발생하는 부분을 수정했습니다. 특히 민감정보 처리와 복호화 결과 Schema에서 발생한 오류도 테스트 결과를 분석하여 원인을 찾아 해결했습니다.

Case, Evidence, Artifact, Search, Timeline 등 주요 화면을 우선 구현하고 실제 엔진 결과를 연결할 수 있는 구조를 만드는 것이 목표입니다. 또한 FTK Imager와 Autopsy를 대상으로 준비한 벤치마크 시나리오를 정리하고, 동일한 조건에서 성능과 기능을 비교할 수 있도록 실제 검증 준비도 진행할 예정입니다.

<시도한 것>
APEX 디지털 포렌식 코어 엔진의 소스 코드와 JSON Schema가 실제 동작과 일치하는지 점검하고, 발견된 차이를 수정하려고 했습니다. 특히 Case, Search, Report, AI Assistance, Hash Verification, 복호화 및 민감정보 처리 부분을 중심으로 Runtime과 Schema를 비교했습니다. 수정 이후에는 pytest, Ruff, mypy와 Schema 검증 도구를 이용하여 기존 기능에 문제가 생기지 않았는지 확인했습니다.

<실패한 것과 그 원인 분석>
KakaoTalk 복호화 관련 테스트를 진행하던 중 실제 복호화 자체는 정상적으로 이루어졌지만 Schema 검증에서 실패하는 문제가 발생했습니다. 확인 결과 실제 비밀값인 pragma_key와 user_nonce를 차단하기 위한 민감정보 정규식이 pragma_key_hash와 user_nonce_hash 같은 안전한 SHA-256 해시값까지 비밀정보로 잘못 판단하고 있었습니다. 처음에는 decryption-result.schema.json에 해당 정규식이 있을 것이라고 생각하고 수정하려 했지만 실제 정규식은 공통으로 사용하는 common.schema.json에 정의되어 있어 수정되지 않았습니다.

<해결을 위해 시도한 것>
먼저 Schema Validation 오류의 정확한 경로를 출력하여 문제가 발생한 필드가 pragma_key_hash와 user_nonce_hash라는 것을 확인했습니다. 이후 schemas/v1 전체에서 관련 정규식을 검색하여 common.schema.json에 정의되어 있다는 것을 찾았습니다. 원본 pragma_key와 user_nonce는 계속 차단하면서 뒤에 _hash가 붙은 안전한 Fingerprint 값은 허용하도록 정규식을 수정했습니다. 이후 실패했던 KakaoTalk 테스트부터 다시 실행하고 Secret 및 Decryption 관련 테스트, 전체 pytest, Ruff, mypy, Schema 검증까지 순서대로 진행했습니다. 최종적으로 전체 테스트가 정상적으로 통과했습니다.

<배운점 및 추후 계획>
오류가 발생했을 때 단순히 테스트를 통과하도록 코드를 수정하는 것이 아니라 실제 원인이 Source, Schema, 공통 정의 중 어디에 있는지를 먼저 확인하는 것이 중요하다는 것을 배웠습니다. 또한 보안 관련 정규식은 너무 넓게 설정하면 정상적인 데이터까지 차단할 수 있기 때문에 원본 Secret과 Hash/Fingerprint를 명확하게 구분해야 한다는 점도 알게 되었습니다. 추후에는 기능을 추가할 때부터 Source, Schema, Test를 함께 확인하여 서로 다른 상태가 되지 않도록 관리하고, 프론트엔드와 MCP 연동 과정에서도 동일한 계약을 사용하도록 검증할 계획입니다.
