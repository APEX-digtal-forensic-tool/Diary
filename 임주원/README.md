# 2026.09.16.

팀명 : APEX

<일주일 동안 내가 만들어 낸 것(만들어낸 것이 없으면 노력한 것, 학습한 것도 가능)>
이번 주에는 APEX Digital Forensic Tool의 CORE가 실제 환경에서 정상적으로 동작하는지 확인하기 위해 WSL2 환경에서 CLI 통합 테스트를 진행했습니다.

APEX의 Python 실행 환경을 구성하고 pytsk3, Registry Parser, Event Log Parser, Prefetch Parser, Browser Cryptography, Impacket, PDF Renderer 등 포렌식 분석에 필요한 주요 기능의 동작 가능 여부를 확인했습니다.

이후 별도로 제작된 APEX_CLI_TEST_BUNDLE을 이용하여 Evidence 등록, 파일 해시 검증, RAW 이미지 처리, 파일시스템 인덱싱, Windows Artifact 분석, Browser 분석, Registry, Event Log, Prefetch, Media, Search, Timeline, Context, Report 등의 기능을 실제 CLI에서 순차적으로 테스트했습니다.

최종적으로 총 54개의 CLI 테스트 시나리오를 실행하였으며, 예상하지 못한 실패 없이 모든 테스트가 PASS하는 것을 확인했습니다. 이를 통해 현재 WSL2 환경에서 APEX의 주요 분석 파이프라인이 정상적으로 연결되어 동작하고 있다는 것을 확인했습니다.

<일주일 동안 겪었던 힘든 점, 극복했다면 해결 방법>
힘든점 : 처음 테스트 환경을 구성했을 때 Python 패키지를 설치했음에도 APEX 실행 과정에서 cryptography 모듈을 찾을 수 없다는 오류가 발생했습니다.

확인 결과 일반 Python 환경에 설치된 패키지와 APEX가 uv를 통해 실제로 사용하는 가상환경이 서로 달랐습니다. 또한 프로젝트가 Windows 파일시스템인 /mnt/c 경로에 있었기 때문에 해당 위치에 가상환경을 생성하는 과정에서 Impacket 설치 시 파일 생성 오류가 발생했습니다.

이를 해결하기 위해 APEX 전용 Python 가상환경을 WSL의 Linux 파일시스템 내부에 따로 생성하고, uv가 해당 환경을 사용하도록 설정했습니다. 이후 필요한 의존성을 다시 설치하여 APEX의 주요 기능이 정상적으로 인식되는 것을 확인했습니다.

환경 문제를 해결한 이후에도 테스트 프로그램이 case create 단계까지만 실행되고 종료되는 문제가 발생했습니다. 로그에는 오류가 없었기 때문에 테스트 러너의 코드를 직접 분석했고, 테스트 프로그램에서는 case_id와 evidence_id라는 JSON 필드를 기대하고 있었지만 현재 APEX CLI는 id라는 필드로 반환하고 있다는 것을 발견했습니다.

이에 테스트 러너가 기존 형식과 현재 형식을 모두 지원하도록 수정한 뒤 다시 테스트를 진행했고, 전체 54개 시나리오를 정상적으로 완료할 수 있었습니다.

<내가 잘한 것과 더 잘할 수 있었는데 아쉬웠던 점>
잘한것 : 단순히 오류 메시지에 따라 패키지를 반복적으로 설치하지 않고, 실제 APEX가 어떤 Python 환경을 사용하고 있는지 확인하여 시스템 Python 환경과 프로젝트 가상환경이 분리되어 있다는 근본적인 원인을 찾았습니다.

또한 테스트가 오류 없이 중간에서 종료되는 상황에서도 APEX CORE 자체의 문제라고 바로 판단하지 않고 테스트 러너의 코드와 APEX가 반환하는 데이터 구조를 비교하여 인터페이스 불일치를 찾아냈습니다.

결과적으로 파일시스템, Browser, Registry, Event Log, Prefetch, Media, Search, Timeline, Report 등 주요 기능을 포함한 54개의 CLI 시나리오가 모두 정상 통과하는 결과를 얻었습니다.

아쉬웠던점 : 처음부터 프로젝트별 Python 가상환경을 완전히 분리해서 구성했다면 의존성 충돌과 환경 문제를 더 빠르게 피할 수 있었을 것 같습니다. 또한 이번 테스트는 대부분 명령 실행의 성공 여부를 검증한 것이기 때문에, 실제 분석 결과가 기대한 값과 정확히 일치하는지까지는 아직 충분히 검증하지 못했습니다.
