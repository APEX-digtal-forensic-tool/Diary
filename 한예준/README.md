지난번에 찾아낸 백엔드 버그 6건을 실제로 고쳤다. 사건별 권한이 토큰 전체 합집합으로 계산되던 A04, 비활성 사용자도 refresh가 되던 A05, 세션 행 없이 승인 grant가 만들어지던 A11, 다른 사건 증거를 가리키는 정정 기록이 체인 검증을 통과하던 A08, tasks.json이 깨지면 로컬 API가 죽던 A10, kid 배열이 들어오면 500이 나던 A12를 전부 수정했고 PR #25로 올려서 main에 머지했다. 고친 뒤에는 처음 버그를 재현했던 스크립트를 그대로 다시 돌려서 6건이 전부 막히는지 하나씩 확인했다.

머지된 코드를 다시 검토하다가 A04가 완전히 닫히지 않은 걸 찾았다. 사건 A에서 ADMIN이고 사건 B에서 ANALYST나 APPROVER인 사용자가 B에서 apex.view.raw_read를 호출할 수 있었다. 원인은 토큰의 scopes 클레임이 모든 사건 권한을 합친 값이라는 점이었다. 그래서 FrontendAuthorizationGate에서 대상 사건마다 case_roles를 보고 필요한 scope를 따로 검사하도록 고쳤고, 경계 케이스 테스트 5개를 추가했다. 이 수정은 별도 PR로 올리도록 정리했다. 머지된 상태는 아니다.

<일주일 동안 겪었던 힘든 점, 극복했다면 해결 방법>
가장 힘들었던 건 A04였다. 처음 PR은 VIEWER만 막았고 다른 역할 조합은 그대로 뚫려 있었다. 머지 뒤에 역할 조합을 표로 만들어 하나씩 돌려본 끝에 합집합 문제가 남아 있다는 걸 알았고, 검사 기준을 토큰 전체가 아니라 대상 사건별로 바꿔서 해결했다. CI의 ruff에서 import 순서 오류가 나서 한 번 고쳤고, 수정 패치를 파일로만 전달해서 내 PC에는 없는 문제도 있었다. 결국 코드 수정 내용을 프롬프트에 직접 넣어서 해결했다.

<내가 잘한 것과 더 잘할 수 있었는데 아쉬웠던 점>
버그를 보고서 글만 믿지 않고 먼저 재현했고, 고친 뒤에도 같은 재현으로 다시 확인한 점이 잘한 부분이었다. 덕분에 머지된 코드에 남은 권한 누수도 찾을 수 있었다. 테스트 통과만 보고 끝내지 않은 게 도움이 됐다.

아쉬운 건 권한 같은 경계 조건을 처음부터 역할 조합별로 테스트하지 않았다는 점이다. 처음 수정에서 VIEWER 하나만 보고 끝냈기 때문에 같은 버그를 두 번 고치게 됐다. 앞으로는 권한을 고칠 때 가능한 조합을 표로 먼저 만들어 테스트에 넣어야겠다.

<다음주까지 해올 것>
고친 내용을 가지고 최종 테스트를 한다. 전체 pytest, ruff, mypy를 다시 돌리고 6건 재현 스크립트도 최종 코드 기준으로 한 번 더 확인한다. 테스트가 끝나면 배포하고, 배포 후에는 실제 환경에서 로그인, 토큰 갱신, 사건별 권한, 증거 정정 같은 흐름이 의도대로 동작하는지 검증받는다. 남아 있는 A04 raw_read 수정 PR도 리뷰를 받아 배포 전에 머지되도록 챙긴다.
