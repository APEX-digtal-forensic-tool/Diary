드디어 백엔드 쪽을 실제로 시작해서 끝까지 만들었다. 로그인하면 토큰을 발급해주고, 그 토큰으로 어떤 사건에 접근 가능한지·어떤 역할(뷰어,분석가,승인자 등)인지까지 확인하는 인증 서버를 FastAPI로 처음부터 구현했다. 민감한 작업을 실행하기 전에 사람이 한 번 승인해야 하는 절차(승인 코드 발급하고 1회만 쓸 수 있게 소비하는 방식)도 같이 만들었다. 그리고 이걸 만들어놓고 끝낸 게 아니라 MCP 서버가 실제로 이 백엔드를 쓰도록 연결까지 끝냈다 — 그동안 MCP는 테스트용 가짜 로그인만 쓰고 있었는데 그걸 진짜로 교체한 거다.
구현 후 코드를 처음부터 끝까지 다시 훑어봤는데, 그 과정에서 실제로 남아있던 버그를 여러 개 찾아서 고쳤다. 여러 요청이 거의 동시에 들어오면 한 번만 쓰여야 할 승인 코드가 두 번 소비될 수 있는 경쟁 조건, 자동 검사(CI)가 실제로는 백엔드 테스트를 한 번도 실행한 적 없었던 문제, 로그 레벨 설정값이 화면에는 보이지만 실제로는 하나도 적용 안 되고 있던 문제 같은 것들이다.
마지막으로 로그인 토큰이 탈취당했을 때 대비하는 보안 기능도 추가했다. 같은 로그인 토큰을 재사용하려고 하면(이미 한 번 교체된 옛날 토큰이 다시 들어오면) 탈취로 보고 그 계정의 세션 전체를 강제로 로그아웃시키는 방식이다. 로그아웃 API도 이번에 새로 만들었다.

<일주일 동안 겪었던 힘든 점, 극복했다면 해결 방법>
보안 기능을 다 만들고 나서 한 가지 빈틈을 발견했다. 로그아웃을 시켜도 이미 발급된 토큰 자체는 만료되기 전까지 실제 분석 기능 쪽에서는 계속 통과된다는 것이었다. 처음 설계할 때 "매번 DB를 확인하지 않고 토큰만으로 빠르게 검증한다"는 방식을 택해서 생긴 부작용이었다. DB를 매번 확인하도록 뜯어고치는 방법도 있었지만, 그러면 원래 설계의 장점(속도, 백엔드가 잠깐 죽어도 나머지 기능은 계속 도는 것)이 없어져서, 대신 토큰 유효기간 자체를 짧게 줄이는 쪽으로 절충했다.
그리고 검증 도중에 실수로 작업 중이던 문서 파일 일부를 지워먹은 적이 있었다. 커밋을 안 해놓은 채로 다른 브랜치 파일을 덮어씌우는 명령을 써버린 게 원인이었는데, 나중에 다시 하나씩 비교해가며 복구했다.

<내가 잘한 것과 더 잘할 수 있었는데 아쉬웠던 점>
뭔가 다 됐다고 보고받아도 곧이곧대로 믿지 않고, 실제로 다시 실행해보고 코드를 직접 읽어서 확인하는 습관을 계속 지킨 점은 잘했다고 생각한다. 그 덕분에 겉으로는 멀쩡해 보였던 보안 빈틈을 배포 전에 미리 찾을 수 있었다.
아쉬운 점은 문서 파일을 다룰 때 커밋을 미리미리 해두지 않아서 한 번 작업분을 날려먹었다는 것이다. 앞으로는 파일을 고칠 때마다 바로바로 커밋해두는 습관을 들여야겠다.
